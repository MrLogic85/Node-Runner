# Save format

The rules for what Node Runner writes to disk, and the choices one file
makes. The fields, types, ranges and defaults are in the records in
`libs/NodeRunner.Domain/` and the schemas in `docs/save-schema/`; a
change to a saved shape changes both, and this document where a rule or
decision changes, in the same PR. What each part means is in
`docs/CREATURE_MODEL.md`, and latest and best in `docs/TRAINING_LOOP.md`
→ "Latest and best ever".

## Rules

1. **Old saves keep loading** as "Project stage" requires.
2. **The records are the shape.** The files serialize the records
   directly through `SaveJson`; only `formatVersion` is outside them.
   `docs/save-schema/` is the exact field list, generated by .NET's
   `JsonSchemaExporter` and kept in step by `SaveFormatTests`.
3. **Loading is strict.** An unknown field, a missing required field or
   a wrong `null` fails with a `JsonException` naming it, from
   `SaveJson`'s options, not a schema validator. They do not check list
   items, so the records reject a `null` part and an out-of-range value
   themselves, and narrowing a range is a format change. A name the
   records know but do not save is skipped.
4. **One JSON style:** camelCase names; enums as camelCase strings, never
   numbers; every field written, an optional one as `null`; GUIDs for
   Creations and positive integers for parts; creature units and
   radians. No number is `NaN` or infinite, except a Locked Brake's
   `strength`, written as `"Infinity"` and read back as one on that field
   only.
5. **Names are free text,** never part of a path, so any name reads back
   as typed; half a UTF-16 surrogate pair is written as `U+FFFD`. The
   format has no length cap, so any saved name loads; the game's limits
   are in `docs/BUILD_MODE.md` → "Rules".
6. **Ids only grow.** `nextPartId` and `nextNeuronId` are above every id
   in use, and a removed id is never reused, so a new part never inherits
   a removed part's weights.
7. **What follows from saved values is never saved:** ports, a joint's
   radius, a Wheel's weight, the compiled network, physics state, the
   number a Memory cell holds, an unfinished generation and the lock
   (`docs/TRAINING_LOOP.md` → "Product lifecycle boundary").

## Layout

The root is Godot's `user://` folder.

```
progression.json                 player progress
settings.json                    the player's settings
creations/<id>/
  creation.json                  the Creation
```

`<id>` is the Creation's id as 32 hex digits without dashes. Deleting a
Creation deletes its folder.

## Project stage

The project stage decides how changes treat data already saved on a
device (Creations, training, progression, settings). `README.md` →
"Status" names the current stage.

| Stage | Saved user data |
| --- | --- |
| **Development with testers** (alpha) | Every Creation and Progression save from 0.13.0 on must load in every later version: a change to their shape migrates older files on load (see "Versions and migration"). Other saved data may still be reset when migrating it is not worth it. |
| **Released** | Everything saved must be migrated. |

## Versions and migration

The baseline is the 0.13.0 shape: every `creation.json` and
`progression.json` that 0.13.0 writes. `settings.json`'s version 1 is
its first shape, in 0.14.4.

- A versioned file starts with `formatVersion`, a whole number. Every
  file has it. The 0.13.0 shape is version 1, and a file without the
  field is version 1.
- Loading reads the version, runs the migrations from that version to
  the current one in order, then loads the result strictly as above.
- A file without the field or in an older version is written back in the
  current version right away, when it is loaded. The write is skipped if
  the file changed after it was read.
- A file newer than the app, one whose `formatVersion` is not a version
  the app knows, or one whose migration fails, is handled as a file that
  fails to load (see "Writing and reading") and is never overwritten.
- `VersionedSaveFile` (`libs/NodeRunner.App/Repositories/`) does this for
  any file; a `SaveMigration` edits the file's JSON one version up before
  the strict load, and its comment says what it changes and why.

### Changing a saved shape

A change to the shape of a file the project stage protects adds a
migration, so the current version goes up by one and older files load in
the new shape, with a test that loads a file in the previous version. A
change that keeps the shape but changes what a saved value means is
migrated too when a migration can keep the old meaning; otherwise the PR
says why it needs none. The `change-saved-shape` skill has the steps.

The real files 0.13.0 wrote are checked in as fixtures in
`tests/NodeRunner.App.Tests/Repositories/SaveExamples/0.13.0/`, and
`CreationVersioningTests` and `ProgressionVersioningTests` load them.
They are never rewritten in place.

### Pinned saves

`EveryPartPinTests` pins a creature that holds every part kind: its
`creation.json`, its network ports and its share code. A refactor must
leave the pins unchanged. A deliberate change rewrites them and commits
them in the same PR, so the review shows what changed.

## Share code

Share build copies the creation as one line of text; Import creation
reads it back. `CreationShareCode` (`libs/NodeRunner.App/Repositories/`)
owns the encoding and its caps.

- It holds the build only: the copy has no training and takes the
  importer's grid default.
- It is made short against its version's share dictionary
  (`libs/NodeRunner.App/Repositories/ShareDictionaries/`), and reading
  puts back what was left out from that dictionary, so a later change to
  Build's defaults never changes an old code. Renumbering keeps the
  ports' order (`NetworkPorts`).
- The dictionary is compressed in front of the code, so the checksum
  catches a changed character, and a code cut short at its end still
  loads if its build is complete.
- A dictionary never changes once released, or its codes stop reading
  (`ShareDictionaryTests`).
- An older code goes through the same migrations as a saved file, and
  Import warns that it may differ from the shared creation. A code from a
  newer version is refused as newer.
- It is someone else's text, so reading it is strict and capped, and a
  build Build could not make, or one with no joints, is refused as
  damaged (`CreatureBuilder.IsWithinBuildLimits`). Its name is cut to the
  creation name limit.
- The copy gets a new id and the name the player gives it on Import.

## Writing and reading

- Every file is written to a temporary file next to it and then renamed
  over it, so a crash never leaves half a file.
- A `creation.json` that fails to load is skipped and logged; the other
  Creations still list.
- A `progression.json` or `settings.json` that fails to load is renamed
  to `<file>.corrupt-<time>`, and progress or settings start fresh.

## File decisions

The choices one file or field makes, with why.

### `creation.json`

- `training` stays `null` until a generation finishes.
- `trainSettings` stays `null` until Train setup's first Start, so until
  then Train setup follows `settings.json`'s Shadows default. `grid` is copied
  from `settings.json` when the Creation is made, so a later change to
  Settings leaves it.
- A Train setup range end or a grid size off its steps loads as the
  nearest step (`RunLengthRangeDef`, `BuildGridDef`), so a hand-edited
  file still loads; any other value out of range fails.
- A part setting left out reads as a new part's; an older file gets its
  values from a migration, never from that default.
- A link side is `null` once its link or Wheel is deleted, and the
  creature cannot train until the player picks one.
- `training.network` is keyed by port (`partId`, `channel`), never by
  list order, so hidden neurons and structural mutation need no new
  format. A port a later version adds has no neuron in an older network,
  plays silent and gets one at the next refit (`docs/CREATURE_MODEL.md` →
  "Sensor–network contract"): it needs no migration.
- Latest and best keep a map's stable id (`MapIds`), so a map's id never
  changes once saved. A save without `frontDistance` shows Latest's score
  and hides the best marker until the next generation is saved.
- A default name is saved in the player's language.

### `settings.json`

- It belongs to the device, not to a Creation.
- A number out of range loads clamped or snapped (`SettingsDef`), so the
  file never fails to load over one; any other value outside the schema
  fails it.
- A UI size above the screen's largest is kept and shown at the largest.
